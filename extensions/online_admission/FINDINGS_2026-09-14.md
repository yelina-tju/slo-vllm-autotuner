## 1. Fixed-grid alignment cost (CPU, no new performance experiment)

Let g be the original cohort-grid origin, W the cohort width, r the actual
settling deadline, and k the number of healthy confirmation cohorts.

```text
first eligible start = g + ceil((r-g)/W) * W
alignment wait       = first eligible start - r       in [0,W)
earliest confirmation = first eligible start + k*W
```

This ignores completion/finalization and tick latency and assumes enough healthy
samples and demand. It is eligibility geometry, NOT a throughput prediction.

For dev201: W=20s, k=2, settling=20s. Exact ack time was not logged, so bound it
between the tick observation and post-application log timestamps:
40.1221704–40.1225757s relative to trace start. Thus fixed-grid alignment adds
**19.8774243–19.8778296s** beyond the settling deadline. Earliest grid confirmation
ends at 120s, explaining the observed terminal 120.097s action.

No safety settings were reduced. Reanchoring future cohorts to the actual
settling deadline is a hypothesis for reducing alignment overhead, not an
implemented or experimentally verified improvement: request membership, minimum
samples, timeout attribution and revision boundaries must remain correct.
Three CPU tests cover grid boundaries, invalid inputs and 2001 phase offsets
without accepting pre-settling evidence.

## 3. Why the abort counter is not an authoritative signal here

Read the actual installed vLLM source after the mismatch; no source was patched:

- async_llm.py:593–598: CancelledError/GeneratorExit invokes abort(..., internal=True).
- async_llm.py:712–721: removes output-processor state and forwards abort IDs to EngineCore.
- output_processor.py:479–498: pops request state and creates local abort output.
- output_processor.py:602–611: later output for absent/already-aborted state is
  skipped BEFORE ordinary iteration-statistics update.
- loggers.py:1144–1147: finish counters increment from iteration_stats.finished_requests.

This implementation explains why a client-aborted request need not increase
request_success_total{finished_reason="abort"}. The metric exists but is not
necessarily comprehensive for this path. The observed cessation of work,
absence of length completion, recovery, and source path support effective
cancellation in these cases; they do not satisfy the original counter criterion.
Request-abort log messages are conditional on log_requests, and this run's
backend log has no matching abort message. Do not fabricate request-level proof.

For a future protocol, add enabled request-level logs/IDs or a dedicated abort
event signal and require it together with engine idle/token plateau/recovery.
Preserve aggregate counter values as diagnostics, not the sole authoritative
abort signal. Review that protocol BEFORE another GPU run. This turn did not
launch a revised probe or change the failed report to passed.
