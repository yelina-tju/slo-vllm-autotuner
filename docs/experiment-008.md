# Experiment 008：静态策略与自适应策略的真实流量对照

本轮的问题是：工作负载改变时，自动切换带来的收益，是否足以抵消检测等待、单卡重启以及准入拒绝的损失？实验 007 已证明切换链路能够工作；本轮检验它在端到端指标上是否值得执行。

## 结果先看

三组共计 11,388 条请求，客户端与 gateway 的请求数量和 HTTP 状态码数量完全一致；没有后端/传输错误。表中的“成功但超时限”表示完成了响应、但至少一项延迟超过该请求的 SLO。

| 策略 | 达标请求数 | 有效吞吐量 | 429 限流 | 503 暂停 | 成功但超时限 | 重启次数 |
|---|---:|---:|---:|---:|---:|---:|
| 固定高准入 | 3,737 | 11.315 req/s | 0 | 0 | 59 | 0 |
| 自适应 | 1,707 | 5.172 req/s | 1,081 | 974 | 34 | 2 |
| 固定保守准入 | 989 | 2.997 req/s | 2,806 | 0 | 1 | 0 |

自适应相对保守静态基线多产生 718 个达标请求，有效吞吐量约高 72.6%；相对高准入静态基线则少 2,030 个达标请求，约低 54.3%。不能只引用前一个数字宣称成功。

再看成功请求的尾延迟：

| 策略 | 短请求 P99 E2E（限 400 ms） | 长请求 P99 E2E（限 500 ms） |
|---|---:|---:|
| 固定高准入 | 411.38 ms，超标 | 560.90 ms，超标 |
| 自适应 | 410.21 ms，超标 | 487.45 ms |
| 固定保守准入 | 349.42 ms | 408.18 ms |

高准入静态策略有更高的有效吞吐量，但不满足按类 P99 约束。保守静态策略的已接纳请求按类 P99 达标，却拒绝了约 73.9% 的到达请求。当前自适应策略没有实现期望中的兼顾，且仍有短请求 P99 超限。本轮的价值在于测出原因，为下一版控制器提供可复现的改进目标。

## 实验设计

三组共用一条事先生成的 Poisson 开环请求序列，seed=81。计划到达时刻、输入 token ID、输出长度和类别均一致，记录请求 payload 的 SHA-256 指纹进行核对。发生拒绝时不重试，客户端按固定计划发出后续请求，不等待前一请求完成；实际发出延迟另行记录。

| 阶段 | 时间区间 | 输入/输出 token | 到达速率 |
|---|---|---|---:|
| balanced_before | 0–60 s | 全部 256/64 | 16 req/s |
| mixed_shift | 60–210 s | 每个请求以 80%/20% 概率选择 256/64 或 2048/64 | 6 req/s |
| balanced_return | 210–330 s | 全部 256/64 | 16 req/s |

类别比例是随机生成的，实际数量以 trace 为准；三组复用同一条 trace，因而类别数量不会在组间漂移。

| 组别 | 启动配置 | 准入上限 | 在线切换 |
|---|---|---:|---|
| static_aggressive | mbt2048 / seq256 / FCFS | 固定 24 req/s | 关闭 |
| adaptive | mbt2048 / seq256 / FCFS | 从 24 req/s 开始，随策略改变 | 开启完整控制器 |
| static_conservative | mbt1024 / seq256 / FCFS | 固定 3 req/s | 关闭 |

这两个静态基线分别代表较高准入与保守准入。它们不是只差一个调度参数的消融实验：配置和准入一起变化，不能把组间差异全部归因于 mbt。

三组都经过同一个 gateway、同样的一秒 token-bucket burst 配置。每组启动时直接向后端预热每类 8 个请求，避免污染控制器的工作负载检测窗口。实验开始后的自动重启及其冷启动成本包含在测量中。

## 统计口径

短请求固定使用 TTFT ≤ 100 ms、E2E ≤ 400 ms；长请求固定使用 TTFT ≤ 295 ms、E2E ≤ 500 ms。评分器按真实请求类别计算，不因当前激活的是哪项 policy 而改变阈值。

- 有效吞吐量 goodput = 同时满足两个延迟限制的成功请求数 / 完整测量时长。
- 429、503、传输失败和延迟超标都不算达标；拒绝请求不会从分母中移除。
- HTTP 200 数量与 SLO 达标数量分别报告，避免把“返回成功”等同于“满足时限”。
- 整体测量时长至少为 330 秒；若最后一批请求延后完成，分母延长到实际完成时刻。
- 分阶段和 30 秒非重叠窗口按计划到达时间划分，因此是 arrival-cohort 指标，不是按完成时刻计数的流出速率。
- tail violation area 在每个窗口、每个类别上取 TTFT/E2E 的最大相对超标量，再乘窗口长度并累加。它只针对成功样本；拒绝数及没有成功样本的类别窗口另列。不能单靠这个面积评价大量拒绝请求的策略。
- 控制器窗口仍为 60 秒、每 10 秒评估一次；30 秒窗口只用于离线对照评分。

比较时需要同时读两类结果：达标请求总量，以及已经接纳请求的尾延迟。较高准入可能产生更多达标请求，但仍因 P99 超限而不满足原有约束；保守限流可能降低尾延迟，却牺牲大量请求。汇总 JSON 中 `all_classes_meet_slo` 使用严格的“无拒绝/失败且 P99 达标”口径，不能把它与离线实验中只针对已接纳后端请求的失败约束混为一谈。上线策略最终还需要明确独立的可用性/拒绝率预算。

## 新增实现

`src/slo_autotuner/comparison.py` 生成固定时间边界的 trace，并计算独立于策略的评分。

`scripts/compare_policies.py` 串行执行各组真实实验，记录逐请求 JSONL、gateway 审计 JSONL、每五秒的策略/准入/GPU 快照以及完整结果。完成的组可按 trace、配置和代码指纹跳过；未完成的组会保留现场并要求使用新的输出目录，避免把两次不同启动拼成一轮结果。

`GatewayRuntime` 新增静态模式；代理路径和准入仍正常工作，但不启动控制循环。切换审计增加开始时间、结束时间、总耗时和是否需要重启，原有执行器流程保持不变。

`scripts/summarize_policy_comparison.py` 核对三组请求 ID、payload 指纹和客户端/gateway 两侧的状态码计数，再输出对照表与时间序列图。

## 自适应策略的时间线与回滚原因

| 时刻（相对流量开始） | 事件 |
|---:|---|
| 60.00 s | 请求分布开始改变 |
| 135.14 s | 控制器确认 mixed_80_20，暂停准入并执行切换 |
| 182.48 s | mbt1024 健康检查通过，以 3 req/s 恢复准入 |
| 192.49 s 左右 | 第一次 SLO 超标告警 |
| 202.49 s | 第二次告警触发回滚 |
| 210.00 s | 输入流量已恢复为全部短请求 |
| 251.02 s | 回滚到 mbt2048，仍以 mixed rollback 的 3 req/s 准入 |
| 330.00 s | 实验流量结束，仍在 300 秒 rollback cooldown 内 |

第一次检测到执行的等待约 75.14 秒。切换和回滚分别耗时 47.34 秒、48.53 秒；合计 95.87 秒，占测量时长约 29%。回滚本身成功执行，但恢复成短请求后，保守准入仍被冷却期保留，因此服务能力没有及时释放出来。

对 gateway 原始审计逐条重建 SLO 窗口后发现：第一次切换后的两个告警窗口，超标请求集合都只有 **request_id=1732**。它在准入恢复后约 0.082 秒进入服务，gateway 测得 TTFT=161.75 ms、E2E=444.40 ms。

| 告警窗口 | 短请求样本数 | 长请求样本数 | 超标请求 ID | 短请求 P99 TTFT / E2E |
|---|---:|---:|---|---|
| 第一次 | 24 | 7 | 1732 | 141.37 / 422.15 ms |
| 第二次 | 44 | 17 | 1732 | 125.75 / 403.66 ms |

第二次窗口没有新的超标请求，却再次包含同一条慢请求。当前实现每 10 秒读取一次 60 秒滚动窗口，因此“两次告警”并不是两批独立坏样本。样本量较小时，单个极端值足以使插值 P99 超限。

这条请求紧邻重启后的重新准入，现象与冷启动瞬态一致；尚未做内核级定位或预热 A/B，不能断言具体是 CUDA Graph、内存分配或哪一层初始化导致。可以确定的是，`/health` 通过只验证服务可响应，并不保证首批请求达到稳态延迟。

回滚后的前几条短请求也产生了相似告警。由于当时已处于该 profile 的 fallback，控制器只发出 alert，没有无限重启。

复核命令：

```bash
python scripts/summarize_policy_comparison.py \
  results/comparison_seed81 --inspect-rollback
```

## 主要运行操作

1. 使用原有 SSH RSA 密钥连接云端，验证主机密钥。
2. 检查进程、GPU、磁盘、旧日志、已有结果；确认没有运行中的实验，显存占用为 0。
3. 校验核心代码 SHA-256，确认本地和云端版本一致。
4. 在云端 `run/pre008-backup` 保存将要更新的旧代码和日志，上传本轮新增脚本。
5. 执行全套自动测试，再启动真实三组对照。
6. 实验结束后校验请求记账、同步结果和审计文件到本地，并确认 GPU 服务已停止。

本轮共 48 项自动测试通过。收尾检查确认 vLLM / gateway / 对照脚本均无运行中进程，8000/8080 端口连接被拒绝，GPU 显存为 0 MiB、利用率为 0%。云端实例本身仍需在平台控制台关机以停止算力计费；本地修改和读文档不需要开机。

## 证据边界

这是一个随机种子、一个阶段时长方案、固定运行顺序的 pilot。逐请求数量较多，不代表有多个独立实验重复。它能测出这一条 trace 上的收益和代价，不能代替多种子、交错运行顺序、不同负载持续时间的实验。先看这轮结果，再确定下一轮该检验的假设。

本轮压测客户端与 gateway 使用同一 Python 进程，模型服务另起进程；重启期间还共享云主机 CPU。自适应组的 P99 客户端发出延迟为约 53.95 ms，高于高准入静态组的约 2.11 ms。计划到达 trace 完全一致，实际发出时刻并不完全相同。延迟主指标从实际发出时刻计时，发出延迟单独保留，因此本轮不应用来声称精确、独立的调度算法性能优势。下一轮应把流量发生器拆成独立进程，并同时报告从计划到达时刻计算的延迟。

## 下一轮应检验的改进

1. 区分健康检查和性能就绪：新实例在暂停准入期间完成受控预热，预热耗时仍计入不可用成本。
2. SLO 回滚要求新的异常证据，或用非重叠评估批次；旧窗口保留用于观测，但不能把同一条慢请求反复当作新确认。同时评估 P99 所需样本量与快速故障响应的取舍。
3. 将需要重载模型的调度切换与无需重载的准入调整分开。研究冷却期是否只限制昂贵重启，以及在有充分证据时如何安全恢复准入。
4. 加入切换收益与成本比较，并补多种子、交错顺序、长短不同的负载阶段。不能根据这一个 pilot 就取消所有保护机制。

以上是本轮证据提出的下一步，尚未修改在线控制语义，也未声称这些改进已经获得实测收益。
